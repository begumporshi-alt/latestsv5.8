02

The engine — who writes what

Every stock change is a frontend flow calling database logic that writes two things in parallel: the FIFO layers, and a journal entry. This is the whole system in one picture.

Read it left to right. Four user flows drive everything. GRN Receive and Stock Adjust create layers through the batch RPCs; POS Sale and Sales Return consume and restore layers through the FIFO engine. Both paths post their journal entries through the same poster, which also keeps the denormalized accounts.balance in step. One thing to note: stock transfers between warehouses also run through the FIFO engine but post no journal entry — correct, since moving stock doesn't change its value. Since 2026-09-01 every flow keeps its books in the database: GRN receives run through the atomic receive_grn() RPC, and sales returns through the equally atomic record_sales_return() RPC — the page-JavaScript journal building is gone.

03

Life of a batch — the FIFO mechanics

A batch (layer) is one purchase of one product into one warehouse at one cost. FIFO means sales eat the oldest layer first, and each layer carries its own price forever — that's what makes COGS exact.

How a layer is born. Four inflows create layers, each with its own credit account: a GRN receive (Cr 2000 AP), opening stock at go-live (Cr 3900 Opening Balance Equity), a stock increase adjustment (Cr 5900 Inventory Adjustment), and a sales-return overflow (new 'return' layer). All debit 1200. The layer then sits in the queue priced at what you actually paid — that cost never changes, even if you later buy the same product dearer.

How it dies — and comes back. A sale consumes the oldest live layers first, records exactly which layers and how many units in invoice_item_batch_consumption, and posts COGS as Dr 5000 / Cr 1200 at the layer cost. A sales return walks those same consumption records and puts each unit back into the exact layer it came from, at the same cost — the ledger ends up exactly as if the sale never happened. Invoice edits and cancels also restore stock, but through a different function (restore_fifo) that refunds to the newest layer instead of the original ones — a subtle cost re-layering covered in finding 8. Stock reductions (create_stock_reduction) consume oldest-first and post Dr 5900 / Cr 1200, leaving a negative audit row behind.

The anomaly state. When a sale asks for more units than the live layers hold, consume_fifo doesn't refuse — it creates a negative ADJ− layer at the product's current (ratcheted) cost_price. The books stay balanced, but the ledger now contains an IOU. Your live data holds 51 such layers worth −৳310,937, plus 11 REDUCE audit rows (−৳114,279), plus 179 zeroed fallback rows left behind by old edits.

04

Anatomy of a sale — the trigger cascade

One POS save is a chain reaction: insert the invoice, then each line item fires three triggers in alphabetical order — deduct stock, consume FIFO, post COGS. No code calls these functions; the table does.

Why this matters: the item insert is the moment inventory, COGS, and the books all move together — automatically, with no application code in the loop. Three triggers fire in alphabetical order: trg_deduct_stock_on_invoice_item (counter and audit movement), trg_invoice_items_cogs (FIFO consumption), and trg_post_cogs_je_on_item_insert (the journal entry, rewritten once per item so the final JE reflects the full invoice). The COGS posted to 5000 is exactly the cost of the specific layers consumed — which is why the batch ledger, not any average, is the only place where true margins can be computed.

The two traps in this design: the triggers fire even when the invoice is a draft (stock and layers are consumed before confirmation — currently latent because no drafts exist), and a shortfall doesn't block the sale — it silently creates the negative ADJ− layer from section 03.

05

Three ledgers, three numbers

The same physical stock is recorded in three places. Each has its own writers and its own readers — and the readers never see the other records.

The counter used to be the dangerous one: the POS checks availability against inventory_items.quantity_on_hand, a denormalized number maintained separately by triggers, RPCs and direct page writes. Its 2026-08-30 rebuild used stock movements rather than the batch ledger, so everything that touched layers without writing movements left it behind — 647 pairs under-counted, 21 over-counted. On 2026-09-01 it was rebuilt from batch truth (migration 20260901130000: 666 pairs corrected, 1 missing row created, per-pair audit in inventory_counter_rebuild_audit). Drift is now zero, and the 30 remaining negative counters honestly mirror negative batch sums. Drift can no longer hide: the Dashboard runs a live reconciliation check (get_inventory_reconciliation(), shipped 2026-09-01) and a nightly pg_cron job snapshots it to inventory_reconciliation_log.

06

The data model

Eight tables carry the whole story. The dashed links are the audit's key relationships — records that should mirror each other but have no database constraint keeping them in step.

The two dashed links are the audit in miniature. inventory_items should equal the sum of each product+warehouse's layer quantities — nothing in the database enforces that; 668 pairs disagreed before the 2026-09-01 rebuild (zero today, and the Dashboard's live reconciliation check now catches any return). journal_lines on account 1200 should equal the value of the layer ledger — that holds only if every layer was born and consumed through a journalized path, which is exactly what the ৳7.47M cutover baseline broke until JE-964716 closed it. Also worth knowing: stock_movements (6,313 rows) is a pure audit trail with a no-op GL trigger, and invoice_item_batch_consumption is the quiet hero of the system — it's what makes returns batch-accurate and the COGS audit page possible.
