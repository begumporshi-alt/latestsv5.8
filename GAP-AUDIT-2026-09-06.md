# CRM Gap Audit — 2026-09-06

Scope: the customer lifecycle — customer master → quotation → invoice/POS sale → delivery → collection → dues/aging → returns/refunds → store credit → advances → credit control → relationship layer → reports. Branch `customer-search-improvements`, live Supabase DB used as ground truth.

Method: complete-gap-audit skill (page enumeration → schema ground truth → coverage matrix → 8 gap patterns → evidence verification). This report reports; it does not fix.

## 1. Executive summary

**Gap counts: 4 × P1, 8 × P2, 7 × P3.** (The original P0 — delivery dead-end — was **withdrawn** the same day: the delivery page has always had a working per-row status dropdown; see P0-1.)

**Fix status (same day, three batches):** batch 1 (commit `675b1c6`) — P1-1, P1-3, P1-4, P2-1. Batch 2 (`b3ac147`) — P1-2 (credit gate + computed overdue) and the POS expiry half of P2-6. The transactional core is solid: `customers.outstanding_balance` is trigger-maintained and reconciles exactly against invoice dues + manual receivables on every live record checked (delta ৳0). Invoices, payments, returns, advances and store-credit redemption all have working create paths with GL posting.

The three worst gaps in plain language:

1. **`customers.total_purchases` is silently corrupted by the app itself — ৳270,757.09 of overstatement across 37 customers (max ৳48,000).** A DB trigger recomputes the column from invoices + manual receivables, but four client-side flows write to it anyway, on top of the trigger's value. Every POS sale and every quotation conversion overstates it again; every collected manual receivable adds a phantom purchase. The CRM pages hide this because they recompute the number client-side — the stored column is just wrong.
2. ~~**Delivery fulfillment is create-only.**~~ **WITHDRAWN — audit error.** The delivery page has always had a per-row status dropdown wired to `updateStatus`; all six states are reachable and the 8 pending rows were never trapped. Details in §3 (P0-1). *Credit control (item 3 below) was fixed the same day.*
3. **Credit control is decoration.** `credit_limit` and `credit_days` are displayed and filterable, but no checkout, invoice, or job ever enforces or uses them; the `overdue` invoice status has no writer (0 rows ever) and the customer "Since" filter on the CRM list is computed but never applied — it filters nothing. *(Fixed: credit gate at POS + invoice form, overdue computed from due_date, due-date defaults from credit_days.)*

The "relationship" layer of the CRM is schema-only: `customer_notes` (with a 5-type note taxonomy), `customers.assigned_to`, `tags`, `notes`, `tax_id`, `loyalty_points`, and the whole `warranty_records` table have **zero references in the app**. No live rows are trapped in any of them (all empty).

## 3. Gap list

### ~~P0-1~~ — Delivery dead-end: **WITHDRAWN — audit error**
- The original claim was that no UI can transition a delivery out of `pending`. **That was wrong.** The delivery page's row-actions cell has always contained a status `<select>` wired to `updateStatus` (`delivery/page.tsx:300-306`), which writes any of the six statuses and stamps `delivered_at` on delivered. The 8 pending rows were simply never progressed, not trapped — the 59 delivered / 2 failed rows were produced by this dropdown, not by an earlier UI.
- Root cause of the false claim: the evidence greps surfaced `delivery/page.tsx:109` as the only other `.from('deliveries')` write and the action-cell render (lines 296-308) was never read — a MISSING claim was accepted without the grep-level proof of absence the audit method requires.
- What legitimately remains: transitions are **unrestricted** (any status → any status, no state-machine guard — e.g. pending → delivered directly), which is a P3 polish option, not a gap. And by design (owner-approved): marking a delivery `returned` does NOT restore FIFO stock — stock restoration stays the sales-return flow's job, preventing double-restoration.

### P1-1 — `customers.total_purchases` corrupted by competing client-side writers (live drift ৳270,757.09 / 37 customers)
- **Stage:** collection/reporting. **Pattern:** denormalized balance drift.
- Ground truth: trigger `sync_customer_total_purchases` recomputes `total_purchases = Σ invoices(non-cancelled) + Σ manual-receivable JEs` on every invoice INSERT/UPDATE/DELETE. The app then writes the column directly in four places, on top of the recomputed value:
  - POS checkout: `pos/page.tsx:800-804` (`+ total` after the trigger already counted the sale) → stored value overstated by the last POS sale at all times.
  - Quotation convert: `quotations/page.tsx:1665-1671` (`+ totalAmount` after inserting the invoice) → same overstatement.
  - Manual collection: `CollectPaymentModal.tsx:305` (`+ form.amount` when *collecting* a receivable — the debit was already counted at creation) → every collected manual receivable double-counts.
  - Record receivable: `RecordButton.tsx:181-186` and `accounting/page.tsx:1014,1319` (`+ amount`) — consistent with the formula's intent, but bypasses the trigger and races it.
- **Verified:** SQL against live DB: 37 customers drifted, max Δ ৳48,000, Σ|Δ| ৳270,757.09. CRM pages display client-computed `total_purchases_calc`, so the visible dashboards are right — the stored column (read by `accounting/page.tsx:961` and carried through edits) is wrong.
- **Fix sketch:** delete all four client-side writes; extend the balance-recompute trigger to also fire on `journal_entries` (the supplier side already does this via `supplier_balance_on_journal_entry`); one-time rebase `UPDATE customers SET total_purchases = <truth>` (same shape as the AR rebase in the journal audit). Route: [[denormalized-balance-drift]], [[frontend-flow-to-atomic-rpc]].
- **FIXED 2026-09-06:** exactly this. `recompute_customer_balances()` is now the sole writer, fired from invoices / payments / journal_entries / journal_lines; all client bumps removed (POS, quotation convert, RecordButton, accounting ×2, CollectPaymentModal, advance-apply); audited rebase corrected 37 customers (−৳270,757 purchases, −৳44,325 outstanding on the worst row); postcondition proves 0 drift; live trigger wiring test passed in a rolled-back transaction.

### P1-2 — Credit control is decoration (limit never enforced, `overdue` unreachable)
- **Stage:** credit control. **Pattern:** real-world step with schema+UI display but no enforcement.
- `credit_limit` is read only inside `/crm` (display + filter). POS checkout and the invoice form never compare the resulting outstanding against the limit. Today only 1 of 137 customers has a non-zero limit (31 have `credit_days > 0`), so the exposure is latent but the field invites data that does nothing.
- `invoices.status='overdue'` has no writer — not POS, not sales, not any trigger, no pg_cron job (only migration referencing cron is the inventory reconciliation check). 0 rows ever. `overdue` appears in dead filter arms (`aging:76`, `sales:3130`, `dashboard:687`) and an unreachable badge branch (`crm/[id]:444`).
- **Fix sketch:** warning banner at POS/invoice when `(outstanding_balance + this sale) > credit_limit` — warn-and-confirm, consistent with the oversell gate decision (no hard block); compute overdue for display from `due_date`/`credit_days` rather than storing a fifth status, or add one cron to stamp it. Needs owner input on policy.
- **FIXED 2026-09-06 (owner approved warn-and-confirm + compute-for-display):** `lib/credit-gate.ts` + `CreditConfirmDialog` (z-120, mirrors the oversell gate; fail-open on lookup error; zero-limit customers never gated) wired into POS checkout and the CreateInvoiceModal. Overdue is now computed by `isInvoiceOverdue()` (`lib/format.ts`) and drives the sales-page stats card, the status filter, row badges, the Outstanding Breakdown modal, and the CRM detail badges. The chain was otherwise inert because **all 643 invoices have `due_date = null`** — the invoice modal now defaults due date from the customer's `credit_days` when left empty. Verified live: a ৳69,000 on-credit sale to the one limit-bearing customer (limit ৳50,000, outstanding ৳11,323) fires the dialog with "Over the limit by ৳30,323"; a real ৳180 zero-limit sale passing through the new code during verification was not impeded.

### P1-3 — CRM list "Customer Since" filter is dead
- **Stage:** view. **Pattern:** computed-but-unused filter.
- `crm/page.tsx:135-140` computes `periodCutoff`; it is in the `filtered` useMemo dependency array (`:172`) but the filter body (`:143-171`) never references it. Selecting Last 7/30/90 days / This Year changes nothing on screen.
- **Fix sketch:** add `if (periodCutoff && new Date(c.created_at) < new Date(periodCutoff)) return false;` (or remove the control). Route: [[react-memo-stale-filter]] family.
- **FIXED 2026-09-06:** the cutoff check was added to the filter body; verified live — "Last 7 Days" now narrows the list to 13 of 137 customers.

### P1-4 — Customer detail page: every tab is row-capped and headline stats are computed from the capped rows
- **Stage:** view/report blindness. **Pattern:** silent truncation.
- `crm/[id]:109` invoices `.limit(20)`, `:111-112` quotations/deliveries `.limit(10)`, `:117` payments `.limit(50)`. `totalPaid` / `totalOutstanding` (`:148-149`) are reduced over the 20-row slice, so the receivables summary and the CollectPaymentModal's `invoiceOutstanding` prop are understated for any customer with >20 invoices; the receivables tab hides older unpaid invoices entirely (collection still works — the modal re-queries by status). Customers with 20+ invoices exist (85 sent invoices across the base).
- **Fix sketch:** paginate via the shared `lib/fetch-all.ts` helper, or move the stat queries to a small RPC. Route: [[pagination-search-bug]].
- **FIXED 2026-09-06:** all four queries moved to `fetchAll` with `id` tiebreakers; verified live on the Walk In customer (132 invoices): Total Paid now shows the full ৳120,665.25 and the Payments tab counts 158 (was a 50-row slice).
